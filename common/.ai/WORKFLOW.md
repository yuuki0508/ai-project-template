# AI開発の進め方

このテンプレートを使って実際に開発を進めるための手順書。

- **案件を始めるとき** … 「1. 案件の始め方」
- **毎日の作業** … 「2. 日常の作業」
- **コマンドの意味を忘れた** … 「4. make コマンド早見表」
- **用語が分からない** … 「6. 用語」

プロンプト例はそのままコピーして使える。`<>` の部分だけ置き換えること。

---

## 0. 全体像

回っているループは2つだけ。

**日々のループ（毎日）**

```
タスクを1枚置く → 実装させる → make check を通す
  → make handoff → make done TASK=<名前>
```

**育てるループ（月1回）**

```
make promote → 昇格候補を見る → docs/ か .cursor/rules/ に書く
  → テンプレートに戻す
```

日々のループで「リポジトリに書かれていなかった情報」が自動で溜まり、
月1回のループでそれをルールに変える。**次の案件はそのルールを最初から持って始まる。**

覚えるコマンドは実質2つ。`make handoff` と `make done TASK=<名前>`。

---

## 1. 案件の始め方

### 1-A. 新規案件

テンプレートのディレクトリで `init.sh` を実行する。

```bash
cd ~/dev/ai-project-template
./init.sh --out ~/dev/<案件名>
```

対話で案件名・タイトル・1行説明・スタックを聞かれる。一括指定もできる。

```bash
./init.sh --out ~/dev/shift-kanri \
  --name shift-kanri --title "シフト管理" \
  --oneliner "店舗スタッフのシフトを作成・共有する" \
  --stack laravel-mysql --yes
```

生成後にやること。

```bash
cd ~/dev/shift-kanri
make init      # フレームワークの雛形生成（案件で1回だけ）
make up
make check     # ここが通ることを最初に確認しておく
```

そして**必ず先に `docs/00_overview.md` と `docs/glossary.md` を埋める。**
ここが空のままだとAIの精度が上がらない。手で書かず、AIに書かせてよい（後述）。

### 1-B. 既存案件（保守中のシステム）への移植

`init.sh` は使わない。**既存リポジトリに骨格だけを移植する。**

#### 移植するもの

テンプレートの `common/` から、既存リポジトリのルートへコピーする。

```
.ai/prompts/          そのまま
.cursor/rules/        コピーしてから中身を書き直す（重要）
docs/                 空の雛形をコピー。中身を埋めるのが第0週の作業
tasks/                そのまま
bin/promote-check.sh  そのまま
Makefile.handoff.mk   そのまま
AGENTS.md / CLAUDE.md そのまま
.editorconfig         既存に無ければ
```

**持ち込まないもの**: `compose.yml`、`stacks/` 配下。既存の環境が正。

既存リポジトリの `Makefile`（無ければ新規作成）の末尾に1行追加する。

```makefile
include Makefile.handoff.mk
```

`Makefile` を新規作成した場合は `help` ターゲットも作っておく。

```makefile
help: ## コマンド一覧
	@grep -hE '^[a-zA-Z_-]+:.*?## .*$$' $(MAKEFILE_LIST) | awk 'BEGIN{FS=":.*?## "};{printf "  \033[36m%-11s\033[0m %s\n", $$1, $$2}'
```

`-h` を忘れるとコマンド名が全部 `Makefile` と表示される。

#### 第0週にやること（1週間かかる。ここが案件の成否を決める）

保守案件でAIが失敗する原因は能力ではなく**前提の欠落**。
既存システムの暗黙知はあなたの頭の中にあり、AIには見えていない。それを外に出す。

**1日目: 環境コマンドの登録**

既存システムでいつも打っているコマンドを Makefile に書き写す。

```makefile
WEB = docker compose -f docker/compose.dev.yml exec web

up:   ## 起動
	docker compose -f docker/compose.dev.yml up -d
down: ## 停止
	docker compose -f docker/compose.dev.yml down
sh:   ## コンテナに入る
	$(WEB) sh
logs: ## ログ追尾
	docker compose -f docker/compose.dev.yml logs -f

check: lint typecheck  ## AIはこれを通すこと
lint:
	$(WEB) npm run lint
typecheck:
	$(WEB) npx tsc --noEmit
```

**`make check` が最優先。** これが無いとAIは自分の出力の正否を確認できない。
テストが無いなら lint と型チェックだけでよい。網羅性より、**1コマンドで合否が出ること**。

**2日目: 既存システムの文書化（AIにやらせる）**

```
このリポジトリ全体を読んで、docs/00_overview.md を埋めてください。

- システムの目的、主要な業務フロー
- ディレクトリ構成と、各層の責務
- 外部連携（DB、外部API、バッチ、cron）

推測が入る箇所は「※要確認」と明記すること。私が検証します。
まだ他のファイルは変更しないでください。
```

出てきたものを読み、事実と違う部分を直す。「※要確認」に答える。
同じ要領で `docs/glossary.md` も作らせる。**業務用語とコード上の名前の対応表**になる。

**3日目: 実際の規約の抽出（AIにやらせる）**

```
既存コードから、実際に守られている規約を抽出して
.cursor/rules/10-conventions.mdc に書いてください。

- 命名規則（クラス、メソッド、変数、DBカラム）
- レイヤ間の依存方向
- エラーハンドリングの方針
- テストの書き方（あれば）

README に書いてある建前ではなく、コードの実態を読んでください。
複数のやり方が混在している場合は、どちらが新しいかも書いてください。
```

**「あるべき規約」ではなく「実際にそうなっている規約」に合わせる。**
そうしないと追加した機能だけコードが浮く。

**4〜5日目: 触ってはいけない領域の明示（手作業）**

`.cursor/rules/00-project-context.mdc` にあなたが手で書く。ここはAIには判断できない。

```markdown
## 触ってはいけない領域

- `app/Legacy/` … 2019年の旧実装。動作理由が不明なため変更禁止
- `database/migrations/` の既存ファイル … 追加のみ。既存は編集しない
- `config/payment.php` … 決済代行の仕様に直結。変更時は必ず相談すること
```

`10-conventions.mdc` は毎回読まれるので、ここに書けばAIは常に知っている状態になる。

#### コストの判断

第0週は案件全体の約1割。**2〜3ヶ月の案件なら回収できる。**
2週間程度の改修案件なら割に合わないので、`.cursor/rules/` と `tasks/` だけ持ち込み、
`docs/` の整備は省く。

## 2. 日常の作業

作業の種類ごとに分けて書く。上から順に進むわけではなく、必要なものを使う。

### 2-1. 設計する

要件を `docs/10_requirements.md` に落とす。**手で全部書かない。**
顧客のメール、議事録、Excelの要望一覧をそのまま渡してドラフトを作らせる。

```
以下は顧客との打ち合わせ議事録です。
これをもとに docs/10_requirements.md を書いてください。

- 機能要件は「誰が何をできるようになるか」の形式で
- 議事録から読み取れないことは推測せず、「※要確認」として一覧にすること
- 既存システムのどこに影響しそうかも併記すること

<議事録を貼る>
```

**あなたの仕事は「※要確認」に答えること。** そのまま顧客への確認事項リストになる。

#### 方式を決める

同じ要件でも実装の道は複数あり、どれを選ぶかで3年後の保守性が変わる。

- 既存テーブルにカラムを追加するか、新テーブルを作って join するか
- 既存の `OrderService` を拡張するか、新しいサービスクラスを分けるか
- バッチで日次処理するか、リアルタイムに処理するか

**判断はあなたがする。AIにはできない。**
3年後に誰が保守するか、顧客がどこまで運用に耐えられるか、
既存コードのどこが壊れやすいかを知らないため。

ただし**選択肢の洗い出しはAIにやらせられる。**

```
docs/10_requirements.md の「予約のキャンセル履歴を保持する」について、
実装方式の選択肢を3つ挙げてください。それぞれについて:

- 既存コードのどこを変更する必要があるか（ファイル名まで）
- 既存機能への影響
- 3年後の保守性

私が選んだら ADR に起こします。まだ実装はしないでください。
```

選んだら ADR に残す。

```
案Bを採用します。docs/decisions/_template.md の形式で
docs/decisions/0002-cancel-history-separate-table.md を書いてください。
「結果として受け入れる不利益」も必ず埋めること。
```

### 2-2. タスクを起票する

**`_template.md` を手で埋めない。** チャットで説明したあと、起票させる。

```
今の話を tasks/_template.md の形式で
tasks/active/T-003-password-reset.md に起票してください。

触ってよいファイルは、実際に変更が必要なものだけを列挙すること。
00-project-context.mdc の「触ってはいけない領域」に該当するものは
除外し、その旨を明記してください。
```

**あなたがレビューするのは「触ってよいファイル」の欄だけ。**
`10-conventions.mdc` に「そこに書かれた対象ファイル以外を変更しない」と書いてあるので、
この欄がAIの行動範囲そのものになる。余計なものが入っていたら削る。

粒度は**1枚あたり半日〜2日**。`active/` は同時に1〜2枚まで。
細かく切りすぎると `make done` の回数が増えて handoff が形骸化する。

タスクをまとめて分割させる場合。

```
docs/10_requirements.md をもとに、tasks/_template.md の形式で
タスクに分割してください。1枚あたり半日〜2日で終わる粒度。
まだファイルは作らず、一覧だけ出してください。
```

一覧を確認してから作らせる。すぐ着手しないものは `tasks/` 直下に置き、
着手するときに `active/` へ移す。

### 2-3. 実装させる

```
tasks/active/T-003-password-reset.md に従って進めてください。
```

これだけでよい。タスクファイルに範囲と完了条件が書いてある。

**細かい調整はチャットに書く。** ファイルに書き戻す必要はない。

| ファイルに書く | チャットに書く |
|---|---|
| 何が終われば完了か | 「そこはもっとシンプルに」 |
| 触ってよいファイル | 「その変数名は〇〇にして」 |
| やらないこと | 「一旦戻して」 |
| 完了条件 | 試行錯誤、対話 |

判断基準は**セッションが切れても価値が残るか**。

#### make check について

`10-conventions.mdc` に「`make check` を通すこと」と書いてあるので、
AIは実装後に自分で叩き、落ちたら自分で直す。

**ただし自動で走る仕組みは入っていない。** git hook でもCIでもない。
AIが叩かずに「完了しました」と報告することがある。

- タスクファイルの完了条件に `- [ ] make check が通る` を入れる（雛形に入っている）
- **`make done` の前に、あなたが1回叩く**

### 2-4. テストを書く

テストが無い既存システムの場合、**全体にテストを書こうとしない。** 案件が破綻する。

現実的な範囲は2つだけ。

- 今回追加する機能のコードにテストを書く
- 既存コードは、**今回変更する箇所だけ**「変更前の挙動を固定する」テストを書く

2つ目が特に有効。既存メソッドを触る前に、現在の入出力をそのままテストにする。
仕様が正しいかは問わない。**変更しても壊れていないことだけを保証する。**

```
app/Services/OrderService.php の calculateTotal() を変更する前に、
現在の挙動を固定するテストを書いてください。

仕様の正しさは問いません。今返している値をそのまま期待値にしてください。
代表的な入力パターンを5つ選び、それぞれなぜ選んだかも添えてください。
```

新機能側のテスト。

```
tasks/active/T-003-password-reset.md で実装した機能のテストを書いてください。
既存のテストが無いため、テストの置き場所とファイル名の規約も提案してください。
提案を私が承認してから書き始めてください。
```

テストが増えてきたら `make check` に足す。

```makefile
check: lint typecheck test
test:
	$(WEB) npm test
```

### 2-5. 調査・デバッグ

既存システムの挙動を調べるとき。**タスクファイルは不要。**

```
ログイン後に稀にセッションが切れる不具合を調査しています。
関連しそうなコードを読んで、原因の候補を3つ挙げてください。
まだ修正はしないでください。
```

原因が特定できて修正が2〜3ファイルに及ぶなら、そこで起票する。
1行の修正なら起票しない。

仕様書と実装がズレていないか調べるとき。

```
.ai/prompts/02-audit-spec-drift.md の内容を貼る
```

### 2-6. セッションを終える

```bash
make handoff
```

プロンプトがクリップボードに入るので、Cursorに貼る。
AIが `ask` / `redo` / `oral` を列挙して `docs/decisions/_inbox.md` に追記する。

作業ログも残す場合は `.ai/prompts/03-close-session.md` を先に使う。

**「同じ説明を2回したか」を思い出す作業は不要。** AIが会話を全部持っているので列挙はAIの仕事。

### 2-7. タスクが完了した

```bash
make check                          # 自分で1回通す
make done TASK=T-003-password-reset # .md は付けない
```

`TASK=` に渡すのは**ファイル名から `.md` を除いたもの**。ディレクトリ名も付けない。

```
tasks/active/T-003-password-reset.md
              └───────────┬──────────┘
                       ここだけ
```

自動で起きること。

- 今日の観測ログが無ければ**ブロックする**（handoff の叩き忘れ防止）
- `tasks/done/2026-09-03-T-003-password-reset.md` へ移動
- 案件の inbox から横断inbox（`~/ai-knowledge/_inbox.md`）へ集約
- 昇格候補を判定して表示

**表示された候補にその場で対応しなくてよい。** 見るだけでいい。

本当に観測ログが無い場合のみ `FORCE=1` を付ける。常用するようになったら
`.ai/prompts/handoff.md` が重すぎるサインなので削ること。

### 2-8. 久しぶりに再開する

```
.ai/prompts/04-resume-project.md の内容を貼る
```

`tasks/done/` の直近と `_inbox.md` の未昇格ログを読ませて、状況を把握させる。

## 3. 月に1回: 昇格

ここだけが人間の判断。30分程度。

```bash
make promote
```

出力はこうなる。

```
== 横断ルールへ昇格 (10-conventions.mdc) ==
  naming-convention          |  3件 / 2案件  [shift-kanri, ec-site]

== 案件内の決定へ昇格 (decisions/NNNN-*.md) ==
  soft-delete                |  2件           [shift-kanri]
```

やること。

| 手順 | 内容 |
|---|---|
| 1 | 候補の keyword で `~/ai-knowledge/_inbox.md` を検索し、元の観測を読む |
| 2 | 案件内候補 → `docs/decisions/NNNN-*.md` に ADR を書く |
| 3 | 横断候補 → **テンプレートの** `common/.cursor/rules/10-conventions.mdc` に書く |
| 4 | テンプレートを commit / push する |
| 5 | `make promoted KW=<keyword> NOTE=<昇格先>` で昇格済みに記録する |
| 6 | 表記ゆれを統合する |

**4番までやって1セット。** 案件側だけ直すと次の案件で同じ説明を繰り返すことになる。

5番を忘れると、その keyword は翌月以降も候補に出続ける。
`make promoted` は現在の件数を一緒に記録するので、**昇格後に再発した場合だけ
「ルールが効いていない」として再浮上する。**

```bash
make promoted KW=soft-delete NOTE="shift-kanri/decisions/0002"
→ 昇格済みに記録しました: soft-delete （現在 2 件）
```

**6番が仕組みの生命線。** `naming-convention` と `naming-rule` のような
重複keywordを手で1つにまとめる。放置すると重複が検出されなくなり、
`make promote` が何も出さなくなる。

### 昇格先の判断

- **その既存システム固有のもの**（例: レガシー層の扱い、独自の論理削除方式）
  → 案件の `10-conventions.mdc` に留める。テンプレートに戻さない
- **どの案件でも通用するもの**（例: マイグレーションの既存ファイルは編集しない）
  → テンプレートへ戻す

固有のものをテンプレートに戻すと、次の案件で無関係な制約を毎回読ませることになる。

### 最初の1〜2ヶ月

**昇格は起きない。** 1案件目は inbox が溜まるだけ。
2案件目に入って初めて横断の重複が見え始める。

ただし**保守案件は例外**で、同じコードベースを何十タスクも触るため
案件内での再現が早く出る。3ヶ月あれば案件内昇格は回る。

その間は `make handoff` → `make done` を習慣にすることだけを目標にする。

## 4. make コマンド早見表

| コマンド | 意味 | いつ | 誰が |
|---|---|---|---|
| `make help` | コマンド一覧 | 忘れたとき | あなた |
| `make init` | フレームワークの雛形生成 | **案件で1回だけ** | あなた |
| `make up` | コンテナ起動 | **その日の作業開始** | あなた |
| `make down` | コンテナ停止 | その日の作業終了 | あなた |
| `make restart` | 再起動 | 設定変更後 | あなた |
| `make rebuild` | イメージ再作成 | ランタイムのバージョン変更後 | あなた |
| `make logs` | ログ追尾 | 調査時 | あなた |
| `make sh` | コンテナに入る | 調査時 | あなた |
| `make check` | lint + 型 + テスト | **実装のたび** | **AIが自分で** |
| `make fmt` | 自動整形 | lint が落ちたとき | AI |
| `make lint` / `stan` / `test` | check の個別実行 | 切り分け時 | AI |
| `make migrate` | マイグレーション | DB変更時 | AI |
| `make fresh` | DB作り直し + 初期データ | データが壊れたとき | あなた |
| `make handoff` | 引き継ぎプロンプトをコピー | **セッション終了時** | あなた |
| `make done TASK=<名前>` | タスク完了 | **タスク完了時** | あなた |
| `make inbox-sync` | 横断inboxへ集約 | `done` が自動で呼ぶ | 自動 |
| `make promote` | 昇格候補の判定 | 月1回 | あなた |
| `make promoted KW=<keyword>` | 昇格済みとして記録 | 昇格したとき | あなた |

**あなたが日常的に叩くのは `up` `down` `handoff` `done` の4つだけ。**

`make up` / `down` は案件全体ではなく**その日の開発の開始と終了**。
実体は `docker compose up -d` / `down` なので、PCをつけっぱなしなら `down` は省いてよい。

## 5. 手動 / AI の切り分け

### AIにやらせるもの

| 作業 | 理由 |
|---|---|
| `docs/00_overview.md` の初稿 | コードを読めば書ける |
| `docs/glossary.md` の初稿 | 同上 |
| `10-conventions.mdc` の抽出 | 実態はコードにある |
| `10_requirements.md` の初稿 | 議事録があれば起こせる |
| タスクファイルの起票 | 形式が決まっている |
| ADR のドラフト | 選択肢の整理は得意 |
| 実装方式の選択肢の洗い出し | 影響範囲の調査は得意 |
| テストコード | 挙動の固定は機械的 |
| `_inbox.md` への観測ログ追記 | 会話を全部持っている |
| `make check` の実行と修正 | 自動化されている |

### あなたがやるもの

| 作業 | 理由 |
|---|---|
| 「触ってはいけない領域」の指定 | **AIには判断できない。事故防止の本体** |
| タスクの「触ってよいファイル」のレビュー | AIの行動範囲そのもの |
| 実装方式の**決定** | 3年後の保守性、顧客の運用は知らない |
| 「※要確認」への回答 | 顧客とあなたしか知らない |
| `docs/` の初稿のレビュー | 推測が混ざる |
| 昇格の判断と実行 | 固有か横断かの見極め |
| keyword の表記ゆれ統合 | 自動化できていない |
| `make done` 前の `make check` | AIが叩き忘れることがある |

### やってはいけないこと

- **`_inbox.md` を人間が書く** … AIが書く場所。人間が書くと形式が崩れる
- **`~/ai-knowledge/` を自動コミットする** … 顧客名を目視せずに push することになる
- **タスクファイルに仕様を書く** … `docs/` と二重管理になる
- **ADR を書き換える** … 覆すときは新しいADRを書いて古い方を「廃止」にする
- **既存システム全体にテストを書こうとする** … 案件が破綻する
- **固有のルールをテンプレートに戻す** … 次の案件で無関係な制約を読ませることになる

## 6. 用語

### ADR（Architecture Decision Record）

設計判断の記録。1決定1ファイル、連番で `docs/decisions/` に積む。

仕様書は「**今どうなっているか**」を書く場所。ここに「なぜそうしたか」を書くと
仕様の更新のたびに理由が消える。ADRは「**なぜそうしたか**」を時系列で積む別の場所。

保守案件で一番困るのはこの部分。コードを読んでも「なぜ既存テーブルを拡張せず
新テーブルにしたのか」は分からない。理由が分からないと「直していいのか」を判断できず、
結局誰も触れなくなる。

形式は `docs/decisions/_template.md`。実例は `0001-record-decisions.md`
（**ADRを書くという決定自体がADRになっている**）。

**覆すときは書き換えず、新しいADRで置き換える。**
古い方に「状態: 廃止（ADR-0002 に置き換え）」と書く。

### ask / redo / oral

`make handoff` でAIに列挙させる3種類のイベント。
すべて**「リポジトリのどこにも書かれていなかった情報」の検出**が目的。

| 種別 | 何が起きたか | 検出できる理由 |
|---|---|---|
| `ask` | AIがあなたに質問した | **質問した = どこにも書いていなかった証拠** |
| `redo` | AIが誤った方向に実装し、差し戻した | 前提が伝わっていなかった証拠 |
| `oral` | 口頭で伝えた前提のうち、ファイルに無いもの | 次のセッションで失われる |

実例。

```
- 2026-09-03 | shift-kanri | soft-delete  | ask  | 論理削除済みを一覧に含めるか確認された
- 2026-09-03 | shift-kanri | legacy-layer | redo | app/Legacy/ を変更した。触ってはいけない領域
- 2026-09-05 | shift-kanri | soft-delete  | oral | 論理削除は deleted_at ではなく status=9
```

1行目と3行目が同じ `soft-delete` なので、2回目の時点で `make promote` が候補として出す。

**あなたの記憶に依存しないのが要点。**
「同じ説明を2回したか」は思い出せないが、「AIが質問したか」は会話に事実として残っている。

保守案件では `ask` が最も多く出る。既存システムの暗黙知が最も欠落しているため。
**`ask` が減っていくことが `docs/` が育っている指標になる。**

### 横断inbox（`~/ai-knowledge/_inbox.md`）

案件をまたいだ観測ログの集約先。**知識そのものではなく、まだ知識になっていないものの待機列。**

- **AIには読ませない。** 読むのは `promote-check.sh` と月1回のあなただけ
- 案件リポジトリの外にあるため、どのバックアップにも含まれない
- ただし各案件の `_inbox.md` から `make inbox-sync` で**再構築できる**

```bash
# 全案件から一括再構築
for d in ~/dev/*/; do [ -f "$d/Makefile.handoff.mk" ] && (cd "$d" && make inbox-sync); done
```

再構築で戻らないのは**手で編集した結果だけ**（表記ゆれの統合、`x ` マーク）。
git 管理する価値はそこにある。

**顧客名（案件slug）が1ファイルに集まる。** 顧客案件を含む場合、
GitHub への push は契約を確認してから。ローカルの `git init` だけでも
編集ミスからの復旧という価値は得られる。

`handoff.md` の内容欄に固有名詞を書かせないこと。
`soft-delete | ask | 論理削除の扱いを確認された` は問題ないが、
`○○銀行の与信区分をどう持つか` は避ける。

### 昇格

観測ログを、次から自動で読まれるルールに変えること。

| 条件 | 昇格先 |
|---|---|
| 同一 keyword が同一案件で2回以上 | 案件の `docs/decisions/NNNN-*.md` |
| 同一 keyword が2案件以上で出現 | テンプレートの `10-conventions.mdc` |

閾値は `THRESHOLD=3 make promote` で変更できる。

## 7. よくある詰まり

**`make done` が「今日の観測ログがありません」で止まる**
→ `make handoff` を先に実行し、出たプロンプトをAIに貼る。
本当に何も無ければ `FORCE=1` を付ける。

**`make promote` が何も出さない**
→ 正常。1案件目・最初の1〜2ヶ月は昇格候補は出ない。
数ヶ月経っても出ない場合は keyword の表記ゆれを疑う。`make promote` の
「全 keyword」欄に似た名前が並んでいたら統合する。

**昇格済みの keyword が候補に出続ける**
→ `make promoted KW=<keyword>` を実行し忘れている。実行すれば以後は除外される。

**「昇格後も再発している」に出た**
→ ルールを書いたのにAIが同じ質問を繰り返している。`10-conventions.mdc` の
書き方が曖昧か、`globs` の条件から外れて読まれていない可能性がある。
書いた場所と表現を見直す。

**AIが「触ってはいけない領域」を触った**
→ タスクファイルの「触ってよいファイル」に余計なものが入っていないか確認する。
再発したら `10-conventions.mdc` に明記する（`redo` として inbox に落ちているはず）。

**AIが `make check` を通さずに完了と言う**
→ `make done` の前に自分で叩く。タスクファイルの完了条件にも入れておく。

**新しいチャットでAIが前提を知らない**
→ `.ai/prompts/04-resume-project.md` を貼る。
毎回同じことを説明しているなら、それは `oral` として inbox に落ちるべき情報。

**Windows で横断inboxが2つできた**
→ Git Bash と WSL で `$HOME` が違う。`make done` を叩くシェルを1つに固定する。
